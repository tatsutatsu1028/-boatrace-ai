## 1. 学習データの欠損原因

### 1-1. 現状の中身（実測）

| ファイル | 使い道 | 期間 | 日数 | レース数 | 列 |
|---|---|---|---|---|---|
| `sample_history.csv` | 1着モデル（`auto_random_fix.py` / `prediction.py` の本番学習） | 2026-05-19〜2026-08-17 | 91日（欠落日なし） | 14,376 | 13列（勝率・当地勝率・モーター/ボート2連率・平均ST・着順のみ） |
| `history_full.csv` | 2着・3着モデル、決まり手集計、コース基準 | 2026-06-01〜06-24 と 2026-09-08〜09-26 | 43日 | 6,391 | 27列（展示タイム・チルト・展示ST・気象・決まり手など） |

`history_full.csv` の空白は **2026-06-25〜2026-09-07 の75日間**（9/7も欠けている）。

### 1-2. `sample_history.csv` が 8/17 で止まっている理由

**結論: そもそも自動更新する仕組みが存在しない。手作業でアップロードされた一回きりのファイル。**

- Git履歴上、このファイルの変更は4回だけで、すべて作者本人の「Add files via upload / Delete」（GitHubのWeb画面からの手動アップロード）。
  - 2026-08-15 14:09 初回アップロード
  - 2026-08-18 08:16〜08:34 差し替え（削除→再アップロード）← この時点のデータが 8/17 まで
- リポジトリ内のどのスクリプト・ワークフローも `sample_history.csv` を**書き込んでいない**（読み込みのみ: `auto_random_fix.py:663`, `prediction.py`, `backtest_tilt_first_model.py`）。生成元のスクリプトもリポジトリに入っていない（おそらくローカルPCで作成）。
- 8/18 以降は学習データの拡充が `history_full.csv`（`collect_history.py`）側に移ったため、`sample_history.csv` は放置された、という経緯と読める。

→ 「更新が止まった」のではなく「最初から更新されない設計」。

### 1-3. `history_full.csv` に 6/25〜9/7 の空白がある理由

**結論: ワークフローの不具合ではなく「収集の途中打ち切り → 再開されなかった」＋「日次自動収集は開始日以降しか取らない」の組み合わせ。**

GitHub Actions「Collect History」の実行履歴（全22回）を確認した結果:

| # | 日時(UTC) | 種別 | 結果 | 内容 |
|---|---|---|---|---|
| 1 | 09-05 13:47 | 手動 | キャンセル | 5分で手動停止 |
| 2 | 09-05 13:54 | 手動 | キャンセル | 1.5時間で手動停止（遅すぎたため改修→再実行と推測） |
| 3 | 09-05 15:41〜20:41 | 手動（期間 6/1〜8/31, 5時間） | 成功 | **5時間の上限に到達し 6/1〜6/24 の 1,732レースで打ち切り** |
| 4〜22 | 09-08 以降 毎日 | 定期（前日分） | すべて成功 | 9/8分〜9/26分を毎日追加 |

- #3 はワークフローの設計どおり `--max-hours 5` で時間切れ終了し、集めた分だけコミットした（ログ: 行数 20,791）。コメントにも「同じ期間を指定して再実行すれば続きから再開する」とあるが、**その再実行が一度も行われていない**。
- 9/8 のコミット `72849a3` で毎日 00:30 JST に「前日分だけ」を取る定期実行が追加された。最初の定期実行は 9/8 15:45 UTC（= 9/9 00:45 JST）で、取得対象は 9/8。**過去分をさかのぼる機能はない**ので、6/25〜9/7 は誰も取りに行っていない。
- 定期実行 19回はすべて成功、各回13〜16分で終了しており、日次収集自体は正常に動いている。

補足: #3 の実測速度は 1,732レース / 5時間 ≒ **約350レース/時**。日次実行は 1日分（約150〜190レース）を約13〜15分で取っており ≒ 約700レース/時。

### 1-4. 空白期間を後から埋められるか

**埋められる。** 公式サイト（boatrace.jp）の出走表・直前情報・結果ページは日付指定（`hd=YYYYMMDD`）で過去日も表示でき、`collect_history.py` は取得済みレースを自動スキップする再開機能を持っている。

- 方法: Actions「Collect History」を手動実行し、`start=20260625` `end=20260907` `max_hours=5` を指定。終わらなければ同じ条件でもう一度実行（続きから再開）。
- 量の見積もり: 75日 × 約150レース/日 ≒ **約11,000〜12,000レース**。350〜700レース/時なら **16〜33時間 ≒ 5時間実行 × 4〜7回**。
- 注意: `_flush()` は新しい列が増えた時だけヘッダを書き直す方式なので、日付順ではなく末尾追記になる。学習側が日付でソートしているか確認しておくと安全（現状の学習コードは `race_date` 順序に依存していないように見えるが、時系列分割のバックテストでは要ソート）。
- `sample_history.csv` の 8/18 以降を同じ形式で延ばすことも技術的には可能（5項目＋着順は出走表と結果ページにある）。ただし生成スクリプトがリポジトリに無いので、`history_full.csv` から同じ13列を切り出して作る方が確実（`history_full.csv` の列は `sample_history.csv` の列を包含している: racer_id→racer_number の名前違いのみ。※`sample_history.csv` は4〜6着も実着順だが、`history_full.csv` は4着以下をすべて4で保存している点は違う）。

## 2. 過去データの取得可否（公式サイトから1〜2年分さかのぼれるか）

### 2-1. 確認方法

このコンテナからは boatrace.jp に直接つながらないため、調査ブランチ専用の一時ワークフローを GitHub Actions 上で動かし（調査後に削除済み。スクリプトは `docs/data_investigation/probe/probe_official.py`）、**実際に過去日のページを取得して確認**した（1.5秒以上の間隔、合計数百リクエスト程度）。結果の生データ（ページ本文の抜粋を含む）は調査後に削除した。

確認した日付: 2026-09-20 / 2026-03-01 / 2025-10-01 / 2025-04-01 / 2024-10-01 / 2024-04-01 / 2023-10-01 / 2022-04-01 / 2020-04-01 / 2015-04-01 / 2010-04-01

- **出走表・直前情報・結果の各ページ: 2020-04-01 まではすべて取得できた**（既存の `official_fetcher.py` のパーサでそのまま読めた）。2015年・2010年は開催一覧が空で取得できず。→ **過去1〜2年分は問題なく取れる**。
- **公式ダウンロード（競走成績Kファイル・番組表Bファイル、LZH形式）: 2015-04-01 分まで取得できた。** 1日1ファイル（全場分）で約20〜40KB。boatrace.jp の「ダウンロード・他」ページで公式に提供されているもの。
- `robots.txt` は boatrace.jp・www1.mbrace.or.jp ともに `Disallow:`（空 = 全許可）。サイトポリシーは「大量の情報送受信及び大量のアクセスなど、本サイトの運営に支障を与える行為」を禁止しているが、自動取得そのものを禁止する条文はない（詳細は 5章）。

### 2-2. 項目別の結果

| チルト | ◎ | 直前情報ページ | 2020年分でも取得（-0.5〜1.0）。Kファイルには無い |

| 安定板使用 | ○ | 各ページのレース名横（「安定板使用」） | おまけ。全期間で確認 |

### 2-3. おすすめの取り方（2系統の併用）

1. **公式ダウンロード（K/Bファイル）で土台を作る** — 1日1ファイルなので2年分でも約1,460ファイル。着順（全艇）・実進入コース・ST・展示タイム・決まり手・天候・風向・風速・波高・レース種別・何日目・進入固定・全国/当地勝率・モーター/ボート2連率・級別・体重をまとめて取れる。
2. **直前情報ページ（1レース1ページ）で K/B に無いものを足す** — チルト・部品交換・プロペラ・展示ST・展示進入・気温・水温。
3. 出走表ページ（1レース1ページ）は F数・L数・モーター3連率・グレードが必要な場合だけ。グレードは開催一覧（1日1ページ）で足りる。

## 3. 過去の結果から計算で作れる項目 — 何年分あれば安定するか

### 3-1. 前提（手元データからの実測）

- 全国で1日あたり約155レース、1場あたり年間 **約1,800〜3,000レース（中央値 約2,370）**（`sample_history.csv` 91日分から換算）。
- 全国のコース別1着率: 1コース 54.4% / 2コース 14.0% / 3コース 12.9% / 4コース 9.9% / 5コース 5.9% / 6コース 3.0%。
- 選手1人あたりの出走数: 3か月で中央値 約53走（年換算 約200走）。
- 91日分を前半45日・後半45日に割って場×コース別1着率を比べると、平均で **1コース3.6pt、2〜5コース1.7〜2.4pt、6コース0.9pt** ずれる。つまり「1.5か月分」では場ごとの差を語るにはブレが大きい。

安定の目安は「標準誤差（ブレ幅の目安）が 1コースで±2pt、2〜6コースで±1.5pt 以内」とし、二項分布 `SE = √(p(1-p)/n)` で必要レース数を出した。

### 3-2. 項目別の見積もり

| 項目 | 必要なデータ量の目安 | 推奨 | 理由 |
|---|---|---|---|
| **場×コース別1着率** | 1場あたり 約600レース（≒3〜4か月）で統計的なブレは±2pt以内 | **最低1年、できれば2年** | 数だけなら3〜4か月で足りるが、季節（風向・潮・気温）で1コース勝率が数pt動くため、全季節を1回以上含む1年が最低ライン。モーターは年1回入れ替わるので2年あると入れ替え前後の偏りが平均化される |
| 全国のコース別1着率 | 1か月（約4,600レース）で±0.7pt | 3か月以上 | 全国平均はすぐ安定する。場別の値が少ない時の「縮小推定の基準」として使う |
| **場×コース別の決まり手構成** | 2コース: 年約330勝/場 → 1年で±2.7pt。4コース: 年約230勝/場 → 1年±3.3pt、2年±2.3pt。6コース: 年約70勝/場 → 1年で±6pt、2年でも±4pt強 | **2年**（5・6コースは2年でも不安定。全国値との縮小推定が必須） | 決まり手は「そのコースが勝ったレース」だけが母数になるので、1着率より桁違いに母数が少ない |
| 全国のコース別決まり手 | 現在の `history_full.csv`（6,391レース）でも1〜4コースはおおむね安定 | 6か月〜1年 | 例: 2コース勝ちの57.7%が差し、27.6%がまくり（手元データ） |
| **今節成績**（今節平均着順・今節1着数など） | 計算自体は「その節の結果だけ」でよい（最大7日前まで） | **重みの学習・検証用に6か月〜1年** | 値は当日取得で作れるが、モデルに重みを学ばせるには多数の節で「今節成績→次走結果」を見る必要がある。**注意: `history_full.csv` は4〜6着をすべて「4」で保存しているので、今節平均着順を過去データから再現するには4〜6着の実着順も保存する必要がある** |
| **直近の調子**（直近N走の平均着順・勝率など） | 選手は3か月で約50走。直近30走なら約2か月分の助走期間が要る | **学習期間＋3か月** | 学習期間の初日時点でも「直近3か月」が埋まっている必要があるため、例えば1年分学習するなら1年3か月分の結果が必要 |
| 選手×当地×コース別成績 | 1選手が1場を走るのは年1〜3節（10〜30走）程度 → 自前集計では数年分でも不安定 | 自前集計は非推奨 | 既に公式ページから当地コース別成績を直接取得している（`course_stats_fetcher.py`）ので、そちらを使う方が良い |

### 3-3. まとめ

- **「1年分」あれば**: 全国のコース別率・決まり手、場×コース別1着率、今節成績・直近の調子の学習は一通りできる。
- **「2年分」あれば**: 場×コース別の決まり手（4コースまで）も実用的な精度になり、季節×場の傾向も2サンプル取れる。
- 5・6コースの場別決まり手は2年でも母数不足なので、全国値に寄せる縮小推定（例: `(場の勝数 + 全国率×k) / (場の勝利数 + k)`）とセットにすべき。

## 4. 過去1〜2年分の取得にかかる時間

### 4-1. 前提（実測値）

- 量: 全国 約155レース/日 → **1年 ≒ 56,600レース、2年 ≒ 113,000レース**。
- GitHub Actions（米国のランナー）から boatrace.jp への応答時間: **1リクエスト 約9〜10秒**（今回のプローブ: 待機1.5秒込みで92リクエストに約16.5分。既存 `collect_history.py` のコメント「1リクエストの往復が10秒前後」とも一致）。律速はサーバーの応答待ち。
- 既存の収集（1レース3ページ、6並列）の実績: 5時間で1,732レース（≒350レース/時）、日次実行は約700レース/時。
- 公式ダウンロード（K/Bファイル）は1日2ファイル、1ファイル20〜40KB。
- リポジトリは public なので Actions の実行時間の上限（無料枠）は問題にならない。1回の実行は最大6時間（現状5時間で打ち切り）で、`concurrency` により同時に1本しか走らない。

「負荷をかけない」の基準は **同時接続1〜3本、1リクエストごとに1秒以上の待機、全体で毎秒0.3リクエスト以下** とした（既存の収集は6並列で毎秒0.6リクエスト程度）。

### 4-2. 見積もり

| 方式 | 1年分 | 2年分 | 備考 |
|---|---|---|---|
| **A. K/Bファイルのみ**（1日2ファイル、10秒間隔） | 約2時間（730ファイル） | 約4時間（1,460ファイル） | 1回の実行で終わる。着順・進入・ST・展示タイム・決まり手・風・波・勝率・モーター2連率など |
| **B. 直前情報ページを追加**（1レース1ページ） | 56,600ページ | 113,000ページ | チルト・部品交換・プロペラ・展示ST・展示進入・気温・水温 |
| 　B-1. 同時1本（≒360ページ/時, 0.1req/s） | 約157時間 ≒ **連続6.5日** | 約314時間 ≒ **連続13日** | 最も穏やか |
| 　B-2. 同時3本（≒1,000ページ/時, 0.3req/s） | 約57時間 ≒ **連続2.5日** | 約113時間 ≒ **連続5日** | おすすめ |
| C. 出走表ページも追加（F数・L数・モーター3連率が必要な場合） | Bの2倍 | Bの2倍 | 必要な列が限られるなら後回しでよい |
| 参考: 現行 `collect_history.py` のまま（3ページ/レース、6並列、350〜700レース/時） | 81〜162時間 ≒ 連続3.5〜7日 | 162〜324時間 ≒ 連続7〜13.5日 | 同時6本は上の基準より強め |

**実際の日数（5時間の実行を回す場合）**

- 夜間だけ1日1回（5時間）回す場合: B-2 で **1年分 ≒ 12日、2年分 ≒ 23日**／B-1 で 1年分 ≒ 32日、2年分 ≒ 63日。
- 5時間の実行を1日4回つなげる場合（ほぼ連続）: B-2 で 1年分 ≒ 3日、2年分 ≒ 6日。
- K/Bファイル（方式A）は2年分でも半日以内。**まずAで2年分の土台を作り、Bは新しい月から順にさかのぼって足していく**のが、学習に使える状態までの最短ルート。

### 4-3. 注意点

- 日次の定期収集（毎晩00:30）と同じ `concurrency` グループで回すと、過去分の収集中は日次収集が待たされる。過去分の収集は別グループにするか、日次収集の時間帯を避ける。
- 1リクエスト10秒は海外ランナーからの値。日本国内から実行すれば応答は速くなる可能性が高いが、その場合も待機（1秒以上）は入れたまま、同時数を増やさないこと（速くなった分だけ公式サイトへの負荷が上がるため）。
- `history_full.csv` は1年分で約55MB、2年分で約110MBになる見込み（現在 6,391レース・6.1MB から比例計算）。2年分ではGitHubの1ファイル100MB制限を超えるので、年別・月別にファイルを分けるか、Supabase等に保存先を移すことを検討する。

## 5. ピットレポート

### 5-1. 結論

**「規約上少しでもグレーな場は対象外」という基準に従うと、現時点で対象にできる場は 0場。**
どの取得元も「私的使用を超える利用には権利者の許諾が要る」旨の条文があるか、規約そのものが見つからず確認できないため。使うなら、**BOATRACE振興会（boatrace.jp の運営元）から書面で許諾を得るのが唯一の確実な方法**で、許諾が取れれば boatrace.jp 1か所で全24場をまかなえる。

### 5-2. どこに掲載されているか

#### (a) boatrace.jp（公式・全場共通）: `/owpc/pc/race/pitreport?hd=&jcd=&rno=`

2026-04-25〜09-26 の毎週土曜（23日分、のべ320場・日）を1Rのページで調べた結果:

- **掲載は場ではなく「節」単位で決まる。** 1日あたり0〜2場、のべ場・日の **約7.5%（24/320）** だけに掲載。SG・G1・G2 開催日に出ることが多く、24場すべてに掲載実績がある（例: 5/30 浜名湖、6/27 鳴門 はSG開催日）。
- 掲載される節でも全レースではなく、ページに「ピットレポートは7Rから12Rまでが表示対象」のように範囲が書かれる（観測: 7〜12R が9件、10〜12R が2件、9〜11R が1件、1Rから全レースが12件）。範囲外のレースは「表示対象レースではありません」。
- 中身は「枠・選手・ピットレポート（コメント文）・前走結果」の表形式で、本文は1レース約1,000文字。
- **過去分は残っている。** 2018-04-09・2021-04-02 の住之江で「7Rから12Rまでが表示対象」の表示を確認。本文そのものは 2026-03 の鳴門・2026-05〜09 の各場で確認した（本文はファイルに保存していない）。

→ 掲載があるのは全レースの数%程度なので、点数化しても大半のレースは「情報なし」になる点にも注意。

#### (b) 各場の公式サイト

- 24場のトップページ・スマホ版トップ・サイトマップ・レース情報トップを確認したが、ピットレポートへの固定リンクが見つかったのは **大村だけ**（`omurakyotei.jp/yosou/sp/sankou/report/`「ピットレポート」、`/yosou/pitreport.php`「番記者耳より情報」）。他の場はメニューがJavaScriptで組み立てられているか、各レースの画面の中にしか入口がない可能性があり、静的な確認では掲載の有無を判定できなかった（要確認）。
- 参考: リポジトリ内の `venue_comments.py` は各場サイトの「全選手コメント」（蒲郡・大村・丸亀・鳴門・三国の日付付きPDF/ページ、共通CMS 16場）を取りに行くコードだが、**現在どこからも import されておらず使われていない**。共通CMSのページはURLに日付が無く当日分しか取れない作りなので、過去分の取得にも向かない。

グレーと判断した理由:

1. **ピットレポートの本文は記者が書いた文章（著作物）**。出走表の数字や展示タイムのような「事実のデータ」とは扱いが違う。
2. **このアプリは有料予想（note で1日4本目以降 300円）を出している**（`app_core.py:2727` 付近）ので、「私的使用」の範囲とは言いにくい。
3. 画面に表示せず点数化にだけ使う場合、著作権法30条の4（情報解析のための利用）で認められる余地はあるが、それは法律の解釈の問題で、規約の文面だけからは白と言い切れない。基準「少しでもグレーなら対象外」に当てはまる。

### 5-4. 代わりにできること

- ピットレポートの内容の多くは「機力（伸び・出足）」「整備（部品交換・プロペラ）」の話なので、**事実データで代替**できる: 部品交換・プロペラ新（直前情報）、展示タイム・展示ST・周回/まわり足（オリジナル展示）、モーター2連率・3連率、今節成績。これらは数値・事実の掲載で、今回の基準でも問題ない。
- どうしてもコメント情報を使いたい場合は、BOATRACE振興会へ「本文は表示せず、社内の点数化にだけ使う」旨を伝えて許諾を得る。
